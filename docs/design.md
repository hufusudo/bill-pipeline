## 1. 这是什么、为什么做

每月把微信、支付宝导出的账单传进一个本地网页，程序自动做完数据准备的五步：收集、清洗、校验、整理、基础分析。最后给出三样东西：这个月真花了多少钱，哪类花得最多，这个数为什么和 App 里显示的不一样。

两个用处：

1. 黄飞自己真用。吃饭、打球、买球、出去玩的钱主要从微信和支付宝付出去，两个 App 自带的账单各只看得到一半，还把退款、转账和消费混在一起算。
2. 作品集项目。展示数据准备的完整流程：多来源收集、按规则清洗、能对账的校验、建库整理、用 SQL 做分析。

它是黄飞之前的终端记账本（`~/项目/PythonCode/basics/day9/new_tiny_account.py`）的改进版。改进前后的对比也是项目内容，见第 9 节。

## 2. 目标、非目标、反目标

### 目标（这一版要做到）

1. 在网页上传微信账单（.xlsx）和支付宝账单（格式等样本确认，见 3.2），程序自己认出是哪家的。
2. 按第 4 节的规则清洗，按第 5 节归类。
3. 按第 6 节校验。任何一关不过，整份拒收，并说清原因。
4. 存进 SQLite。同一笔交易不管导入多少次，库里都只有一条。
5. 页面（第 8 节）：导入报告、对账表、归类、月报（本月消费总额、各类消费排行）。
6. README 用英文写：做什么、改进前后的流程对比图、清洗规则、校验、怎么运行。
7. pytest 测试只用造的假账单，离线能跑。

### 非目标（这一版不做）

- 任何 AI 功能，包括大模型自动归类、接 demo B 用中文问账。以后再做，见第 12 节。
- 单笔改类（比如把某笔转账从“其他”改成“运动”），以及 AA 收款和支出的自动抵扣。
- 银行流水、现金手动补记、多用户、登录、部署上线。
- 迁移旧记账本的数据（只有 5 条示例数）。
- 预算、提醒、订阅识别。
- 旧版微信 CSV（金额带 ¥ 的那种）。现在导出的是 xlsx，遇到了再说。

### 反目标（做出来也算失败）

- 真实账单、数据库、交易对方的名字进了 Git，或者被发到网上。
- 对账对不上，页面还显示成功。
- 导入中途出错，库里只留下半份账单。
- 程序遇到没见过的交易类型或状态，自己猜着处理。

## 3. 数据来源

### 3.1 微信（2026-10-29 用黄飞的真实账单核实过）

导出：我 → 服务 → 钱包 → 账单 → 右上角「常见问题」→「下载账单」→「用于个人对账」。一次最多 3 个月，发到邮箱，是加密压缩包，解压密码在「微信支付」的通知里。解压后是 .xlsx。

文件结构：

- 只有一个工作表。表头上方是说明行：标题、微信昵称、起止时间、导出类型、导出时间、`共N笔记录`、`收入：N笔 X元`、`支出：N笔 X元`、`中性交易：N笔 X元`、几行注释、一条分隔线。核实的这份，表头上方有 17 行（含空行），第 18 行是表头。**表头位置不能写死**，要按列名 `交易时间` 去找。
- 表头下面每行一笔交易，末尾没有汇总行。
- 共 11 列：`交易时间`、`交易类型`、`交易对方`、`商品`、`收/支`、`金额(元)`、`支付方式`、`当前状态`、`交易单号`、`商户单号`、`备注`。

| 列 | 情况 |
|---|---|
| 交易时间 | Excel 的日期数字，不是文字，读的时候要换算；时区 UTC+8 |
| 金额(元) | 数字，不带 ¥ |
| 收/支 | `支出`、`收入`，中性交易是 `/` |
| 交易类型 | 见过：`商户消费`、`扫二维码付款`、`转账`、`微信红包`、`零钱提现`、`<平台>-退款`（如 `淘宝平台-退款`） |
| 当前状态 | 见过：`支付成功`、`已转账`、`对方已收钱`、`已全额退款`、`已存入零钱`、`提现已到账` |
| 交易单号 | 全部唯一、纯数字、28–32 位，**去重用它** |
| 商户单号 | 有空的、有 `/`，长短不一，不能用来去重 |
| 商品、备注 | 常是 `/` |

退款在账单里成对出现：一边是原交易（`支出`，状态改成了 `已全额退款`），一边是退款那一条（`收入`，交易类型是 `<平台>-退款`，状态也是 `已全额退款`），两边的笔数和合计金额相同。说明行里的支出合计包含了已退款的原交易，所以 App 显示的支出偏高。

扫二维码付款（状态 `已转账`）多半是扫个人收款码付给小摊、档口。交易对方是个人昵称，光看名字分不出类，只能靠黄飞归类（第 5 节）。

## 4. 清洗规则

“谁定的”一栏有三种写法：

- “黄飞”：黄飞自己定的。
- “AI 提议”：AI 提议、黄飞同意的。
- “类推，待确认”：AI 按黄飞的规则类推出来的，他还没确认。

| 情况 | 怎么认出来 | 怎么算 | 谁定的 |
|---|---|---|---|
| 中性交易（零钱提现、充值、理财、还款等） | 微信 `收/支` 为 `/`；支付宝为 `不计收支` | 不算消费，也不算收入 | AI 提议 |
| 全额退款的原交易 | `支出`，状态 `已全额退款` | 不算消费 | 黄飞 |
| 退款那一条 | `收入`，交易类型以 `-退款` 结尾，或状态 `已全额退款` | 不算收入 | 黄飞（“退款除外”） |
| 转出去的钱（AA 球钱、还朋友饭钱） | `支出`，交易类型 `转账` | 算消费，类别固定为“其他” | 黄飞 |
| 发出去的红包 | `支出`，交易类型 `微信红包` | 和转账一样：算消费，归“其他” | 类推，待确认 |
| 转进来的钱（生活费） | `收入`，交易类型 `转账` | 算收入 | 黄飞 |
| 收到的红包 | `收入`，交易类型 `微信红包` | 算收入 | 类推，待确认 |
| 商户消费、扫码付款 | `支出`，状态 `支付成功` 或 `已转账` | 算消费，按交易对方归类 | AI 提议 |
| 部分退款 | 状态形如 `已退款(￥x)` | 消费按原金额减已退金额；退款那一条不算收入 | 类推，真实数据里还没见过，遇到时和黄飞确认 |
| 失败、关闭的交易 | 状态 `交易关闭`、`支付失败` 等 | 不算（没扣钱） | AI 提议 |
| 没见过的交易类型或状态 | 以上都对不上 | 不猜：标成“未识别”，不计入统计，在报告和对账表里单列，提醒补规则 | AI 提议 |

每一行清洗后都要有结果（消费 / 收入 / 不算）和原因，原因能在报告里分组统计。

## 5. 分类

- 类别：吃饭、运动（打球场地、买球和装备）、娱乐（出去玩）、购物、交通、其他。这是 AI 按黄飞说过的花销拟的，黄飞同意了，以后可以改。
- 消费按 `交易对方` 归类。库里存一张“交易对方 → 类别”的对照表，由黄飞在页面上维护：
  - 第一次导入时，页面列出所有还没归类的交易对方，附上笔数和金额，他逐个选类别，程序记下来。
  - 以后每次导入，只有新出现的交易对方才需要他选。
- 转出去的钱、发出去的红包固定归“其他”，不用归类。
- 还没归类的消费，在统计里显示为“未归类”，总数照样对得上。

## 6. 校验

1. **文件检查**（入口处）：
   - 能不能打开。
   - 是不是认得出的账单：找得到表头那一行和必需的列。
   - 编码对不对，比如支付宝的 GBK。

   哪一项不对就拒收，并说清是哪一项。
2. **第一关：读得全不全。** 逐行加出来的笔数和金额（收入、支出、中性交易各算一遍），必须和说明行写的一模一样。不一样就整份拒收，报告里写明差在哪。支付宝的说明行有没有这些数，看了样本再定。
3. **第二关：对账。** 两个等式：
   - 平台支出 − 各类不算的支出 = 清洗后的消费
   - 平台收入 − 各类不算的收入 = 清洗后的收入

   每个减项都列出笔数和金额。等式不成立，说明规则有漏洞，整份拒收。
4. **第三关：不重复。** 以（来源，交易单号）为唯一键。同一份账单导两次，或者两次导出的时间段有重叠，已经存在的就跳过，报告里写“跳过 N 笔已存在”。同一个文件里交易单号有重复，说明文件异常，整份拒收。
5. **要么全进，要么全不进。** 一份账单的入库放在一个数据库事务里，中途出错就回滚。
6. 金额用整数分（或 Decimal）计算，不用浮点数，对账要对到分。

## 7. 存储（SQLite）

- 至少三张表：
  - 交易表。
  - 导入记录表：文件名、来源、时间范围、笔数、各关校验结果。
  - 交易对方 → 类别的对照表。
- 交易表保留原始各列，再加上统一后的字段：来源、时间、收支方向、金额、清洗结果、原因、类别。以后改了规则，可以重新算。
- 数据库文件放在 `data/` 下，不进 Git。
- 分析用 SQL 写，按月份、类别 GROUP BY 汇总。

## 8. 页面（Streamlit，本机运行）

- **上传**：一次可以拖入一个或多个账单文件。
- **导入报告**：每份文件显示来源、时间范围、各关校验结果、新增几笔、跳过几笔、不算的几笔（按原因分组），以及对账表。
- **归类**：列出未归类的交易对方，附笔数和金额，逐个选类别后保存。
- **月报**：选一个月份，显示本月消费总额、收入总额、各类消费排行（柱状图）。

## 9. 改进前后（写进 README 的流程分析）

- **改进前**（旧终端记账本）：
  - 每笔手动录入，漏记了查不出来。
  - 只存“备注 → 累计金额”，没有日期，也没有逐笔记录。
  - 没法和平台的数对账。
- **改进后**：每月导出 → 上传 → 清洗 → 三关校验 → 归类 → 月报。
- README 里放一张前后对比的流程图（mermaid），再加一张“痛点 → 改进”的表。
- 旧代码不改，也不迁移它的数据，但它的做法沿用到新项目里：

| 旧记账本的做法 | 新项目里对应的做法 |
|---|---|
| 读文件遇到编码错误不崩溃 | 认不出编码就拒收，并说明原因 |
| 先写临时文件再替换 | 用数据库事务 |
| 格式不对先备份，不覆盖原文件 | 拒收，不碰已有数据 |

## 10. 技术与结构

- 技术栈：Python 3.13、pandas（读 xlsx 要用 openpyxl）、sqlite3、Streamlit、pytest。用项目自己的 `.venv`，依赖写进 `requirements.txt`。
- 核心部分（读文件、清洗、校验、入库、分析查询）写成普通的 Python 函数，不依赖 Streamlit。页面只负责收文件、调函数、显示结果。这样核心能用 pytest 测，以后换界面也不用改核心。
- 这一版不调用任何大模型，不联网。

## 11. 隐私

- `data/`、`*.db`、真实的 `.xlsx` / `.csv` 都不进 Git（见 `.gitignore`）。测试用的假账单放在 `tests/fixtures/`，显式放行。
- 测试只用造的假账单，要复现真实文件的结构：说明行、Excel 日期数字、成对的退款、转账、中性交易、重复的交易单号、两次导出时间段的重叠。
- 开发时用真实账单验证，只打印结构和统计数字，不打印交易对方、商品、备注的具体内容。要看明细，先问黄飞。
- 页面只在本机运行。
