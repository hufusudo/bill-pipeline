## 1. 这是什么、为什么做

每月把微信、支付宝导出的账单传进一个本地网页，程序自动做完数据准备的五步：收集、清洗、校验、整理、基础分析。最后给出三样东西：这个月真花了多少钱，哪类花得最多，这个数为什么和 App 里显示的不一样。

两个用处：

1. 黄飞自己真用。吃饭、打球、买球、出去玩的钱主要从微信和支付宝付出去，两个 App 自带的账单各只看得到一半，还把退款、转账和消费混在一起算。
2. 作品集项目。展示数据准备的完整流程：多来源收集、按规则清洗、能对账的校验、建库整理、用 SQL 做分析。

它是黄飞之前的终端记账本（`~/项目/PythonCode/basics/day9/new_tiny_account.py`）的改进版。改进前后的对比也是项目内容，见第 9 节。

## 2. 目标、非目标、反目标

### 目标（这一版要做到）

1. 在网页上传微信账单（.xlsx）和支付宝账单（格式等样本确认，见 3.2），程序自己认出是哪家的。
2. 按第 4 节的规则清洗，按第 5 节归类。
3. 按第 6 节校验。任何一关不过，整份拒收，并说清原因。
4. 存进 SQLite。同一笔交易不管导入多少次，库里都只有一条。
5. 页面（第 8 节）：导入报告、对账表、归类、月报（本月消费总额、各类消费排行）。
6. README 用英文写：做什么、改进前后的流程对比图、清洗规则、校验、怎么运行。
7. pytest 测试只用造的假账单，离线能跑。

### 非目标（这一版不做）

- ~~任何 AI 功能~~：10-29 黄飞决定马上接入，见第 15 节。
- 单笔改类（比如把某笔转账从“其他”改成“运动”），以及 AA 收款和支出的自动抵扣。
- 银行流水、现金手动补记、多用户、登录、部署上线。
- 迁移旧记账本的数据（只有 5 条示例数）。
- 预算、提醒、订阅识别。
- 旧版微信 CSV（金额带 ¥ 的那种）。现在导出的是 xlsx，遇到了再说。

### 反目标（做出来也算失败）

- 真实账单、数据库、交易对方的名字进了 Git，或者被发到网上。
- 对账对不上，页面还显示成功。
- 导入中途出错，库里只留下半份账单。
- 程序遇到没见过的交易类型或状态，自己猜着处理。

## 3. 数据来源

### 3.1 微信（2026-10-29 用黄飞的真实账单核实过）

导出：我 → 服务 → 钱包 → 账单 → 右上角「常见问题」→「下载账单」→「用于个人对账」。一次最多 3 个月，发到邮箱，是加密压缩包，解压密码在「微信支付」的通知里。解压后是 .xlsx。

文件结构：

- 只有一个工作表。表头上方是说明行：标题、微信昵称、起止时间、导出类型、导出时间、`共N笔记录`、`收入：N笔 X元`、`支出：N笔 X元`、`中性交易：N笔 X元`、几行注释、一条分隔线。核实的这份，表头上方有 17 行（含空行），第 18 行是表头。**表头位置不能写死**，要按列名 `交易时间` 去找。
- 表头下面每行一笔交易，末尾没有汇总行。
- 共 11 列：`交易时间`、`交易类型`、`交易对方`、`商品`、`收/支`、`金额(元)`、`支付方式`、`当前状态`、`交易单号`、`商户单号`、`备注`。

| 列 | 情况 |
|---|---|
| 交易时间 | Excel 的日期数字，不是文字，读的时候要换算；时区 UTC+8 |
| 金额(元) | 数字，不带 ¥ |
| 收/支 | `支出`、`收入`，中性交易是 `/` |
| 交易类型 | 见过：`商户消费`、`消费-其他`、`扫二维码付款`、`二维码收款`、`转账`、`微信红包`、`零钱提现`、`<平台>-退款`（如 `淘宝平台-退款`） |
| 当前状态 | 见过：`支付成功`、`已转账`、`对方已收钱`、`对方已退还`、`已收钱`、`已全额退款`、`已存入零钱`、`提现已到账` |
| 交易单号 | 全部唯一、纯数字、28–32 位，**去重用它** |
| 商户单号 | 有空的、有 `/`，长短不一，不能用来去重 |
| 商品、备注 | 常是 `/` |

退款在账单里成对出现：一边是原交易（`支出`，状态改成了 `已全额退款`），一边是退款那一条（`收入`，交易类型是 `<平台>-退款`，状态也是 `已全额退款`），两边的笔数和合计金额相同。说明行里的支出合计包含了已退款的原交易，所以 App 显示的支出偏高。

扫二维码付款（状态 `已转账`）多半是扫个人收款码付给小摊、档口。交易对方是个人昵称，光看名字分不出类，只能靠黄飞归类（第 5 节）。

### 3.2 支付宝（2026-10-29 用黄飞的真实账单核实过）

导出：我的 → 账单 → 右上角「…」→「开具交易流水证明」→「用于个人对账」，发到邮箱。解压后是 `.csv`。

文件结构：

- **编码**：GBK（读的时候用它的超集 GB18030）。按 UTF-8 读会报 `UnicodeDecodeError`。
- **说明行**：表头上方有 23 行。第一行是一条横线；中间依次是姓名、`支付宝账户：[…]`、`起始时间：[…]    终止时间：[…]`、导出交易类型、导出时间、`共N笔记录`、`收入：N笔 X元`、`支出：N笔 X元`、`不计收支：N笔 X元`、8 条特别提示；最后一条横线里写着“支付宝支付科技有限公司 电子客户回单”。表头位置同样不能写死，要按 `交易时间` 去找。
- **列**：13 列，最后一列没有列名，是每行末尾多出来的那个逗号。前 12 列是 `交易时间`、`交易分类`、`交易对方`、`对方账号`、`商品说明`、`收/支`、`金额`、`收/付款方式`、`交易状态`、`交易订单号`、`商家订单号`、`备注`。

| 列 | 情况 |
|---|---|
| 交易时间 | 文字，`YYYY-MM-DD HH:MM:SS` |
| 交易分类 | 支付宝自己的分类，如 `餐饮美食`、`日用百货`、`投资理财`。存进 `tx_type`，不拿来归类 |
| 收/支 | 见过 `支出`、`不计收支`。读进来时 `不计收支` 统一记成 `/`，和微信的中性交易用同一个值 |
| 金额 | 文字形式的数字，不带 ¥ |
| 交易状态 | 这次只见过 `交易成功` |
| 交易订单号 | 每个都带首尾空白（看起来是防 Excel 用科学计数法的制表符），去掉后全部唯一、纯数字、28 或 32 位，**去重用它** |
| 对方账号 | 对方的账号，属于个人信息，用不上，不读 |

支付宝在特别提示第 6 条里说，明细金额直接累加后“可能会和下方统计金额不一致”。黄飞这份账单逐行加出来和说明行完全一致，所以第一关仍按“一模一样”来卡。以后哪份不一致，会被拒收，报告里写清差多少，到时再决定怎么处理。

## 4. 清洗规则

“谁定的”一栏有三种写法：

- “黄飞”：黄飞自己定的。
- “AI 提议”：AI 提议、黄飞同意的。
- “类推，待确认”：AI 按黄飞的规则类推出来的，他还没确认。

| 情况 | 怎么认出来 | 怎么算 | 谁定的 |
|---|---|---|---|
| 中性交易（零钱提现、充值、理财、还款等） | 微信 `收/支` 为 `/`；支付宝为 `不计收支` | 不算消费，也不算收入 | AI 提议 |
| 全额退款的原交易 | `支出`，状态 `已全额退款` | 不算消费 | 黄飞 |
| 退款那一条 | `收入`，交易类型以 `-退款` 结尾，或状态 `已全额退款` | 不算收入 | 黄飞（“退款除外”） |
| 转出去的钱（AA 球钱、还朋友饭钱） | `支出`，交易类型 `转账` | 算消费，类别固定为“其他” | 黄飞 |
| 被对方退还的转账 | `支出`，交易类型 `转账`，状态 `对方已退还` | 不算：钱退回来了，账单里也没有另一条退回记录 | 黄飞（10-29） |
| 发出去的红包 | `支出`，交易类型 `微信红包` | 和转账一样：算消费，归“其他” | AI 提议（10-29 确认） |
| 转进来的钱（生活费） | `收入`，交易类型 `转账` | 算收入 | 黄飞 |
| 收到的红包 | `收入`，交易类型 `微信红包` | 算收入 | AI 提议（10-29 确认） |
| 收款码收到的钱 | `收入`，交易类型 `二维码收款`，状态 `已收钱` | 算收入 | 黄飞（10-29） |
| 商户消费、扫码付款 | `支出`，状态 `支付成功` 或 `已转账` | 算消费，按交易对方归类 | AI 提议 |
| 另一种消费类型 | `支出`，交易类型 `消费-其他`，状态 `支付成功` | 和商户消费一样：算消费，按交易对方归类 | 黄飞（10-29） |
| 部分退款 | 状态形如 `已退款(￥x)` | 消费按原金额减已退金额；退款那一条不算收入 | 类推，真实数据里还没见过，遇到时和黄飞确认 |
| 失败、关闭的交易 | 状态 `交易关闭`、`支付失败` 等 | 不算（没扣钱） | AI 提议 |
| 没见过的交易类型或状态 | 以上都对不上 | 不猜：标成“未识别”，不计入统计，在报告和对账表里单列，提醒补规则 | AI 提议 |

支付宝的规则单独一张表。上表里的中性交易和失败、关闭两条，两家共用：

| 情况 | 怎么认出来 | 怎么算 | 谁定的 |
|---|---|---|---|
| 支付宝的消费 | `支出`，`交易状态` 为 `交易成功` | 算消费，按交易对方归类（转账也一样，靠归类归到“其他”） | AI 提议（10-29 确认） |
| 支付宝的退款、收入、转账等 | 这次的账单里还没出现过 | 不猜：标成“未识别”，出现时再定 | AI 提议 |

每一行清洗后都要有结果（消费 / 收入 / 不算）和原因，原因能在报告里分组统计。

补了规则以后，库里已有的“未识别”交易在下次打开页面时按新规则重新判断，只改这些交易的结果、原因和计入金额。

## 5. 分类

- 类别：吃饭、运动（打球场地、买球和装备）、娱乐（出去玩）、购物、交通、其他。这是 AI 按黄飞说过的花销拟的，黄飞同意了，以后可以改。
- 消费按 `交易对方` 归类。库里存一张“交易对方 → 类别”的对照表，由黄飞在页面上维护：
  - 第一次导入时，页面列出所有还没归类的交易对方，附上笔数和金额，他逐个选类别，程序记下来。
  - 以后每次导入，只有新出现的交易对方才需要他选。
- 转出去的钱、发出去的红包固定归“其他”，不用归类。
- 还没归类的消费，在统计里显示为“未归类”，总数照样对得上。

## 6. 校验

1. **文件检查**（入口处）：
   - 能不能打开。
   - 是不是认得出的账单：找得到表头那一行和必需的列。
   - 编码对不对，比如支付宝的 GBK。

   哪一项不对就拒收，并说清是哪一项。
2. **第一关：读得全不全。** 逐行加出来的笔数和金额（收入、支出、中性交易各算一遍），必须和说明行写的一模一样。不一样就整份拒收，报告里写明差在哪。支付宝的说明行有没有这些数，看了样本再定。
3. **第二关：对账。** 两个等式：
   - 平台支出 − 各类不算的支出 = 清洗后的消费
   - 平台收入 − 各类不算的收入 = 清洗后的收入

   每个减项都列出笔数和金额。等式不成立，说明规则有漏洞，整份拒收。
4. **第三关：不重复。** 以（来源，交易单号）为唯一键。同一份账单导两次，或者两次导出的时间段有重叠，已经存在的就跳过，报告里写“跳过 N 笔已存在”。同一个文件里交易单号有重复，说明文件异常，整份拒收。
5. **要么全进，要么全不进。** 一份账单的入库放在一个数据库事务里，中途出错就回滚。
6. 金额用整数分（或 Decimal）计算，不用浮点数，对账要对到分。

**已知限制**（10-29 审查时发现，先记下，还没解决）：

- **导入以后才退款的交易，库里还按消费算。** 入库以后同一笔交易不会再更新，再导入时遇到已存在的就跳过。比如 10 月买的东西，导出 10 月账单时还是“支付成功”，11 月才全额退款：11 月的账单里只有那条退款（不算），10 月那笔原交易一直按消费算，10 月的消费就偏高。三关都只核对单个文件，所以对账页照样显示“对账平了”。目前见过的 2 笔微信退款，退款和原交易的商户单号都对得上（一个包含另一个），以后也许能靠它把两边配对；2 个样本太少，还不能当规则。
- **支付宝退款没有规则，也不会被标成未识别。** 支付宝只认“支出 + 交易成功”，“不计收支”的一律当中性交易，不提醒。如果支付宝把退款记成“不计收支”、原交易还是“交易成功”，这笔就会被悄悄算成消费。真实账单里还没出现过支付宝退款，它在导出文件里长什么样没有核实，出现第一笔时再补规则。

## 7. 存储（SQLite）

- 至少三张表：
  - 交易表。
  - 导入记录表：文件名、来源、时间范围、笔数、各关校验结果。
  - 交易对方 → 类别的对照表。
- 交易表保留原始各列，再加上统一后的字段：来源、时间、收支方向、金额、清洗结果、原因、类别。以后改了规则，可以重新算。
- 数据库文件放在 `data/` 下，不进 Git。
- 分析用 SQL 写，按月份、类别 GROUP BY 汇总。
- 第二版界面（第 8 节）还要这些查询：
  - 上一个月是哪个月，以及本月比上月的变化。
  - 某月按天的消费。
  - 最近 6 个有数据的月份，每月的消费。
  - 最近几次导入的记录。
  - 未归类的交易对方，以及每个对方最近一笔的来源、类型和时间。
  - 已归类的交易对方，以及各自的类别、笔数和金额。
  - 某月某一类的每一笔消费。
  - 某月的对账（第 8.3 节）。

## 8. 界面（第二版：NiceGUI，本机运行）

第一版用 Streamlit 做的页面，黄飞觉得难看、杂乱。10-29 他提了三点要求：

- 好看、高级。
- 折线图、柱状图、饼图都要有好的动效。
- 一页只做一件事。

上网找了参考（见本节末尾），重做了两版能点的草图，他选了 A：浅色、薄荷绿。草图存在 `.superpowers/brainstorm/`，不进 Git。框架换成 NiceGUI，也是他定的。

### 8.1 原则

- 一页只回答一个问题。
- 每页用一个大数字或一张主图当视觉锚点。
- 每种图只干一件事：构成用环形图；趋势用面积折线和柱状图；对账用瀑布图，y 轴从 0 开始。
- 中性底色，加一个主色：薄荷绿 `#1baf7a`。多留白，少用边框。
- 动效只用来帮人看懂：数字从 0 滚到实际值，图表依次入场，切换页面时淡入。
- 每个数都要能直接读到，不能只靠鼠标悬停：环形图旁边有带金额的列表，趋势页有表格视图。
- 分类颜色按类别固定，不随排名变化：

  | 吃饭 | 运动 | 购物 | 交通 | 娱乐 | 其他 | 未归类 |
  |---|---|---|---|---|---|---|
  | `#1baf7a` | `#2a78d6` | `#eb6834` | `#6250d6` | `#eda100` | `#c3c9d3`（灰） | `#e5e9ef`（浅灰） |

  环形图里的扇区按这个固定顺序排，这样相邻的颜色就是 dataviz 验证脚本检查过的那几对（浅色底上，色盲区分度和正常视力区分度都过关）。右边的列表按金额从高到低排。

### 8.2 结构

左边一条竖向导航，共五页。右上角有一个月份选择器，五页共用。

1. **总览：这个月花了多少，花在哪。**
   - 大数字是本月消费，会从 0 滚到实际值。旁边的小标签写比上月多或少百分之几；上个月没有数据就不显示。
   - 大数字下面一行小字：收入、结余、笔数。
   - 环形图显示本月各类消费，中间写“花得最多：某类 百分之几”。右边是列表：色点、类别、金额、占比。
   - 点环形图的某一块，或者列表的某一行，弹出这一类的每一笔：时间、交易对方、金额。
2. **趋势：花钱的节奏。** 用分段按钮在“按天 | 按月 | 表格”之间切换。
   - 按天：本月每天的消费，面积折线，平滑、渐变填充，标出最高的那天。天数从 1 号画到这个月最后一笔交易那天，还没导入的日子不画成 0。
   - 按月：最近 6 个有数据的月份，柱状图。本月高亮，其他月份变灰，只给本月标金额。
   - 表格：最近 6 个月每月的消费，以及比上月的变化。
3. **导入：这份账单可靠吗。**
   - 一个大拖放区，一次可以拖多份（微信 `.xlsx`、支付宝 `.csv`）。
   - 每份文件导入完，出一张结果卡片：进度条走完后，三关依次打勾（读全了 / 对账平了 / 不重复），并写明新增几笔、跳过几笔。有未识别的交易，卡片上提醒；被拒收的，卡片标红并写明原因。
   - 结果卡片一直留在页面上，直到离开这一页；上传框导完自动清空。
   - 下面列出最近几次导入：来源、时间范围、新增、跳过。
4. **归类：这个交易对方算哪类。**
   - 一次只显示一张卡片：交易对方、笔数和金额、最近一笔的提示（微信写付款方式，支付宝写它自己的分类）。下面是六个类别按钮和“跳过”。点一个类别就保存，并滑到下一张。卡片上方显示“第 i / n 个”。
   - 卡片下面是“已归类”列表，每一行都可以重新选类别，归错了可以改。
5. **对账：钱都去哪了。**
   - 一段话写清：这个月账单里的支出是多少，其中多少不算、为什么不算，实际消费是多少。
   - 瀑布图：账单支出 → 每个不算的原因各一根 → 实际消费。
   - 三个徽章：读全了、对账平了、不重复。能进库的数据都过了三关，所以只要这个月有数据就显示。
   - 收入和中性交易的对账放在下面的小表格里。

### 8.3 数据从哪来

新加的查询见第 7 节。月度对账用库里这个月的明细重新算：账单支出 = 这个月所有支出行的原始金额之和；减项和计入的算法和第二关一样，直接复用第二关的对账函数。

## 10. 技术与结构

- 技术栈：Python 3.13、pandas（读 xlsx 要用 openpyxl）、sqlite3、NiceGUI、pytest。用项目自己的 `.venv`，依赖写进 `requirements.txt`。
- 界面框架：第一版用 Streamlit，第二版换成 NiceGUI 3.18（10-29 黄飞定）。NiceGUI 也只写 Python，底层是 FastAPI 和 Vue/Quasar，ECharts 已经打包在安装包里。
- 核心部分（读文件、清洗、校验、入库、分析查询）写成普通的 Python 函数，不依赖界面。页面只负责收文件、调函数、显示结果。这样核心能用 pytest 测，换界面时核心一行不用改。第二版换框架时，正是这样做的。
- 第一、二版不调用大模型。第三版加了 AI（第 15 节），只有点 AI 按钮或者提问时才联网。

## 15. AI 功能（第三版）

10-29 黄飞决定马上接入 AI，要做两件事：

- 给交易对方建议分类。
- 根据消费回答问题。

另外，分类要能自己添加，AI 只从已有的分类里建议。

### 15.1 分类由用户维护

- 分类存进数据库的 `categories` 表（名字、顺序）。默认 6 个，按环形图验证过的顺序排：吃饭、运动、购物、交通、娱乐、其他。
- 在归类页可以添加新分类。名字去掉首尾空白后为 1–8 个字，不能和已有的重复，不能叫“未归类”。
- 这一版只能添加，不能改名，也不能删除。“其他”一直存在，因为转账固定归到它下面。（AI 提议，10-29 黄飞同意）
- 颜色按分类的顺序自动分配：
  - 前 8 个分类，用验证过的 8 种颜色。新增的颜色也要先用 dataviz 的验证脚本检查。
  - “其他”用灰色，“未归类”用浅灰。
  - 第 9 个及以后的分类用中灰 `#9aa3af`，靠名字区分。

### 15.2 AI 分类建议

- 进入归类页时自动调用：对还没有建议的商户，在后台请求一次 AI，不挡住页面。建议存进库里，下次进来直接显示，不会重复请求。（10-29 黄飞要求：每张卡片下面直接显示 AI 的建议）
- 把所有未归类、而且是商户、还没问过的交易对方发给模型，每 20 个一批（回复短，不容易被截断，第一张卡片的建议也来得快）。每个对方带上：
  - 名字
  - 支付宝自带的分类（有的话）
  - 最近一笔的商品说明（不是“/”的话）
- 个人不发，也就不给建议。个人指交易对方最近一笔是扫二维码付款、转账或红包的。
- 要求模型只返回 JSON，类别只能从当前的分类表里选。如果返回的类别不在表里，或者名字不是我们发过去的，就丢掉这一条。
- 问过但 AI 没把握的，也记进表里（建议是空的），下次不再问。
- 建议存进 `ai_suggestions` 表：交易对方、建议、模型、时间、你最后选的类别。
  - 每张卡片下面直接显示“AI 建议：某类”，旁边有一个“采用”按钮，点一下就归好类；对应的类别按钮也高亮。
  - 没有建议时说明原因：付给个人的不发给 AI；问过但 AI 没把握。
  - 你点了哪个类别（包括“采用”），就记成你最后的选择。
- 归类页显示准确率：在你确认过的建议里，AI 猜对了几个。
- 出错时不崩溃，比如没配 key、网络不通、返回的不是 JSON：页面上提示“AI 这次没给出建议”以及原因，手动归类照常进行。

### 15.3 问答

- 新增第六页“问答”。输入一句中文问题，就能得到回答。回答下面可以展开“这次查了什么”，列出每次调用的工具、参数，以及查到的数字。
- 做法是工具调用（Function Calling）：模型不能直接写 SQL，只能调用下面这些只读查询。查询用的都是库里清洗后的数据，金额换算成元。
  1. 有数据的月份，以及每月的消费、收入合计
  2. 某月概况：消费、收入、各类消费
  3. 某月某一类：合计、笔数、每一笔（最多交回 50 笔）
  4. 某月按天的消费
  5. 某月花得最多的交易对方，前 n 个
  6. 查交易：按月份、类别、关键词、日期范围筛选；支持 offset 分页，默认20笔、最多50笔，合计按全部匹配交易计算
  7. 跨月对比：两月消费、收入、结余与分类变化，程序计算增幅和增长贡献
  8. 日期范围汇总：包含起止日、最多366天，支持按日/月/分类分组，说明无交易月份及实际覆盖
- 循环：快速最多5批查询，深度最多15批，每批最多执行6个工具。查询结束后额外保留一次禁止工具的总结调用；无新增结果连续两批则提前总结，同题重复查询复用结果。
- 时间预算：快速查询60秒、深度180秒，总结另30秒；每请求最多30秒并禁用自动重试。停止后不再启动新调用，在途网络请求可能等到超时退出，迟到结果不回写界面。
- 回答页采用“结论 + 依据”布局，指标与图表来自结构化查询结果。显示查询进度、部分回答/超时/取消/错误状态，可查看历史回答或新建对话。
- 历史只保存在当前页面内存，刷新后清除；发送最近6组受限问答与聚合依据摘要，不重放历史明细。新问题重新查数；切换默认月份保留旧记录但显示范围变化。
- 系统提示里要求模型：
  - 只根据工具查到的结果回答，不编数字。
  - 金额写到分。
  - 查不到数据就直说。
  - 问题里没说月份时，默认用页面右上角选中的月份。
- 发出去的内容：你的问题，以及工具查到的结果（交易对方名字、金额、日期、商品说明、类别）。
  - 个人的名字一律换成“个人收款”，商品说明也不发；花得最多的排行里，个人合成一项。有过转账、红包、扫二维码付款或二维码收款的交易对方就算个人。（黄飞 10-29 同意）
  - 不发：交易单号、商户单号、对方账号、支付方式、备注。
- 出错时不崩溃，页面上提示原因。

### 15.4 评测（能写进简历的数字）

- **分类建议**：准确率从 `ai_suggestions` 表里算，就是你确认过的建议里，AI 猜对的比例。
  - 另有离线打分：把已经归过类的商户发给 AI（不带你选的类别），看它猜对了几个，同时算覆盖率（AI 给了建议的比例）。命令是 `scripts/eval_ai.py suggest`。
- **问答**：准备一组问题模板，比如“10 月一共花了多少”“10 月吃饭花了多少”“10 月哪天花得最多”。
  - 标准答案由程序直接查库得到。
  - 脚本逐题去问 AI，检查回答里有没有标准答案里的那个金额，最后算出正确率。
  - 只在本机运行，结果不进仓库。脚本是 `scripts/eval_ai.py`，只打印问了几题、对了几题；会联网、会花钱，运行前先问黄飞。

### 15.5 配置和测试

- 用 openai 库连 DeepSeek，它和 OpenAI 的接口兼容。DeepSeek 官方文档写明支持 Function Calling 和 JSON Output。
- 配置放在项目的 `.env` 里：`OPENAI_API_KEY`、`OPENAI_BASE_URL`、`AGENT_MODEL`，和 demo B 用的是同样的名字，值可以照抄 demo B。动手前先把 `.env` 加进 `.gitignore`。
- DeepSeek 默认开着思考模式（10-29 查官方文档确认）：
  - temperature 不起作用。
  - 带工具调用时，必须把模型上一轮的 `reasoning_content` 原样交回去，否则报 400。所以问答循环把模型的回复原样追加进对话记录，和 demo B 一样。
  - JSON 模式偶尔会返回空内容，当成“返回的不是 JSON”处理。
  - 思考模式回答会慢一些。嫌慢可以关掉，但要加 DeepSeek 专用的参数，换别家接口时要去掉。
- 测试不联网：用一个假的模型客户端代替，按预先写好的内容返回工具调用和回答。`tests/conftest.py` 让每个测试都看不到 `.env` 和环境变量里的 key。还要专门测一条：发给模型的内容里，不能出现个人的名字。
